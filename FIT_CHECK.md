# Fit Check

A wardrobe companion that answers one question: **what should I wear today?**

Product Owner: Nora. Technical Reviewer: Gabriel. Built in milestones — see
[`FIT_CHECK_ROADMAP.md`](FIT_CHECK_ROADMAP.md) for what is deliberately *not*
here yet, and [`FIT_CHECK_DISCOVERY.md`](FIT_CHECK_DISCOVERY.md) for the
architecture and why it's shaped this way.

This is the as-built record. It grows one milestone at a time.

## The three rules

**1. The closed vocabulary is load-bearing.** Notion `select` / `multi_select`
options are closed: writing an unregistered one returns 400 and **rejects the
whole property patch atomically**, failing unrelated fields silently alongside
it. Fit Check's tags are AI-assigned, so this is a live hazard, not a
theoretical one. [`lib/vocabulary.ts`](src/fit-check/lib/vocabulary.ts) is the
single source of truth: it defines the Notion options, is injected into the
tagging prompt, *and* validates every value before a write. The third layer is
the one that actually saves us — a prompt is a request, not a guarantee.

> Adding an option: **Notion first, then `vocabulary.ts`.** The reverse order
> writes an option Notion doesn't know and takes the patch down.

**2. No new serverless functions.** The repo sits at Vercel Hobby's **12/12**
function cap, counted across every app. A 13th fails the deploy for all of them.
Fit Check adds none: Notion via `api/notion.js`, photos via
`api/notion-upload.js` and `api/notion-photo-proxy.js`, Anthropic called
directly from the browser.

**3. AI is one-shot, at the edges.** Photo → tags. Speech → text. Never in the
recommendation path, which is deterministic, instant, offline-capable and
unit-tested.

---

## Home A / Home B

The Notion option names are **stable keys and never change**. Nora renames the
homes in Settings; the app maps key → display name via `homeLabel()` in
[`lib/config.ts`](src/fit-check/lib/config.ts). Renaming the Notion option
instead would orphan every row referencing it — rule 1 from another direction.
`Both` means "lives in both places" and is not renameable.

## Milestone log

### M1 — Skeleton ✅ (2026-08-06)

Scaffold, design system wiring, PWA, theme, navigation, Settings, Demo Mode,
Notion client, and a wardrobe grid rendering from fixtures.

**Built**

- `lib/vocabulary.ts` — the closed vocabulary + coercion, with a hostile-input
  test asserting nothing unregistered can ever be emitted
- `lib/types.ts`, `lib/config.ts` (on-device settings, home renaming)
- `lib/notionClient.ts` — one `_request` chokepoint, non-2xx throws, 429/5xx
  retry with backoff, 350ms write spacing, cursor pagination, demo fallback
- `models/demoData.ts` — 19 garments / 5 outfits, held to the vocabulary by test
- `components/` — `Navigation`, `WardrobeGrid`, `Settings`
- `public/fit-check-sw.js` — network-first navigations, SWR for assets,
  origin-wide cache hygiene (this repo shares one origin across many apps)

**Decisions worth remembering**

- *Coercion returns `null`, never a default.* A garment silently tagged `Top`
  because the model said `Blouse` is worse than one left untagged for Nora to
  fix. Untagged is visible; wrong is not.
- *Demo Mode is "no token ⇒ fixtures", not a toggle* — WhereItWent's `_demoOr`.
  With a token but no database id the app returns nothing rather than blending
  demo rows into live data, which would be far more confusing than an empty list.
- *`active` is read plainly.* Notion can't distinguish an unset checkbox from a
  false one, so the app writes `Active: true` on create rather than guessing.
- *Identity via token override only.* `index.css` overrides `--color-accent` and
  friends at `:root`; no DS component internals are touched.

**Verified** — `npm test` 2160 passing / 185 files · `npm run typecheck` clean ·
`eslint` clean. In-browser at 375×812: 18 tiles (19 fixtures less 1 archived),
all six category sections, home filter Both 18 / A 14 / B 11, renaming a home
propagates to the filter and persists, no horizontal page scroll, 64px nav.

### M1.1 — Icon (2026-08-06)

Drawn from Nora's own sketch: a rounded near-black tile, one tall needle-thin
sparkle above centre, and a scattered constellation of smaller ones at mixed
sizes, in a violet-to-magenta gradient.

The East-Asian hint Gabriel asked for is carried two ways. The four-pointed
sparkle is already the Japanese *kirakira* mark — that was in Nora's drawing.
Made explicit underneath it: **seigaiha** (青海波), the overlapping-wave pattern
printed on kimono and hanbok textiles for centuries. A cloth pattern under a
wardrobe app, rather than a flag stuck on one. Held at 7% stroke opacity so it
reads as texture, not decoration competing with the sparkles.

Two source SVGs, four generated PNGs:

- `fit-check-icon.svg` — the tile. **Rounded corners**, so it carries
  transparent wedges. Right for the `any` icons; wrong for `maskable`, where
  Android would expose them as notches — so the generator flattens the maskable
  onto the field colour first. Everything meaningful sits inside the safe circle
  (radius 205), so nothing is clipped whatever shape a launcher applies.
- `fit-check-logo.svg` — the mark alone on transparent, for the browser tab.
  Two deliberate differences from the tile, both because it's seen at 32px
  against unknown chrome: the gradient never goes near-white (the tile's pale
  tip vanished on a light toolbar), and the waist is 42 rather than 32 (the
  needle silhouette smudges once it's 27px tall).

Verified by rendering the 32px favicon magnified against both white and dark
browser chrome, and by eye at 192 and 512.

### M2 — Photos ✅ (2026-08-06)

Camera capture, resize, upload, the LQIP, the IndexedDB cache, and photo
guidance. Still no AI — tags are chosen by hand until M3.

**Built**

- `lib/lqip.ts` — the placeholder generator and, more importantly, the
  write-budget guard
- `lib/imageCache.ts` — cache-first photos in IndexedDB, single-flight per
  garment, prune on load
- `lib/useGarmentPhoto.ts` — per-tile hook; keyed on garment id, never on the
  signed URL (which changes every read and would refetch the grid each time)
- `components/AddGarment.tsx` — camera capture, three guidance chips, retake
- `notionClient` — `uploadPhoto` (register + send bytes) and `attachPhoto`,
  both opting into the `2025-09-03` API version that file uploads require

**The spike, and how it changed the design**

The plan assumed a ~24px base64 JPEG would fit Notion's 2000-char rich-text cap.
It does — but the first measurement was misleading and the second overturned it:

1. A Node/sharp spike suggested ~720 chars at 32px/q55.
2. Measuring the **actual** path — the browser's canvas encoder — gave very
   different numbers. At 32px/q55 a noisy source hit 1524 chars (95% of the
   original 1600 guard) and an adversarial one **overran and fell back to flat
   colour**.

The guard worked exactly as designed, which was reassuring. But the real lesson
was in the shape of the data: at 16px a plain image costs ~1060 chars, and at
24px ~1084. **Size is dominated by fixed JPEG header overhead, not pixel data** —
canvas emits the full standard JFIF header and Huffman tables every time. So
shrinking the placeholder buys almost nothing, and 24px is effectively free
quality over 16px.

Settled on **24px at q0.4, guarded at 1800**. Worst measured output is 1312 (66%
of Notion's cap), and all three sources now produce a true LQIP rather than
degrading. Don't "optimise" this by going smaller; it won't help and it looks worse.

**Decisions worth remembering**

- *The row is created before the photo uploads.* If the upload fails the garment
  still exists, named and tagged, with a placeholder — recoverable, and the
  error says so. The reverse order can orphan an upload against no row.
- *Object URLs are deliberately never revoked.* Tiles mount and unmount
  constantly as Nora moves between tabs and filters; revoking on unmount turns
  an already-loaded photo into a broken image the moment it returns. Bounded by
  wardrobe size, and the map dies with the page.
- *`getPhoto` is single-flight.* A 40-tile grid mounting at once makes one
  request, not forty. Tested.
- *Settings has no Save button, on purpose* — config persists on every change.
  That was invisible until it was pointed out, so the screen now says so and
  flashes a confirmation. The obvious "skip the first render" ref for that flash
  is wrong: StrictMode double-invokes effects, so the second pass fires it
  before anything is saved. It keys off the config value changing instead.
- *Nav clearance belongs on the scrolling element, not `<body>`.* `ds/tokens.css`
  sets `height: 100%` on body with border-box sizing, so body padding is part of
  that fixed height rather than space after the content — overflowing content
  runs straight past it and the last row sits under the fixed nav.

**Verified** — `npm test` 2187 passing / 187 files · typecheck clean · eslint
clean. In-browser: LQIP generated through the real canvas encoder across plain /
noisy / adversarial sources (1084 / 1204 / 1312 chars, all true LQIPs); capture
screen, guidance chips and retake render at 375×812; last Settings row clears
the nav by 52px at full scroll; no console errors.
